# Конкурс грантов

Лабораторная работа: модель серверной части без HTTP и консольного интерфейса.
Java 17+, Maven 3.9+, Gson 2.11.0, JUnit Jupiter 5.14.0. Все данные находятся в памяти и исчезают после остановки JVM.

## Запуск проверки

```shell
mvn clean verify
```

Откройте `pom.xml` в IntelliJ IDEA как Maven-проект. Выберите JDK 17 или новее.
Точка входа для клиента — `academy.tochkavhoda.competition.server.Server`.
Класса `main` нет по требованиям архитектуры. Сценарии использования находятся в `TestServer`.

```java
Server server = new Server(new BigDecimal("1000000.00"),
    new BigDecimal("3.0"), Instant.parse("2030-01-01T00:00:00Z"));
ServerResponse response = server.registerParticipant("""
    {"firstName":"Анна","lastName":"Иванова","company":"Старт",
     "login":"startup","password":"example123"}
    """);
// responseCode = 200, responseData = "{}"
ServerResponse session = server.login("""
    {"login":"startup","password":"example123"}
    """);
// responseData = {"token":"..."}; извлечь токен с помощью Gson.
```

Второй конструктор `Server(fund, threshold, deadline, clock)` позволяет задавать время в тестах.
`fund` — неотрицательная сумма с точностью до копеек, `threshold` — число от 1 до 5,
`deadline` — момент X в UTC. Настройки задаёт создатель сервера, отдельной роли администратора нет.

## Контракт API

Все методы возвращают `ServerResponse`: код 200 при успехе, 400 при ошибке.
`responseData` — JSON; ошибка всегда имеет единственное поле `error` с понятным сообщением.
Для операций без результата успешный ответ — `{}`. Регистрация не выполняет автоматический вход.
Все операции, кроме регистрации и входа, требуют токен первым параметром.

| Метод | Поля JSON-запроса | Успешный результат |
|---|---|---|
| registerParticipant(json) | firstName, lastName, company, login, password | {} |
| registerExpert(json) | firstName, lastName, directions, login, password | {} |
| login(json) | login, password | token |
| logout(token) | нет | {} |
| deleteAccount(token) | нет | {} |
| addApplications(token, json) | applications: массив объектов title, description, directions, amount | applicationIds |
| cancelApplication(token, json) | applicationId | {} |
| rateApplication(token, json) | applicationId, score | {} |
| deleteRating(token, json) | applicationId | {} |
| getOwnApplications(token) | нет | applications |
| searchApplications(token, json) | directions | applications |
| getRatedApplications(token) | нет | applications |
| getResults(token) | нет | awards, remainingFund |

Пример подачи нескольких заявок:

```json
{"applications":[
  {"title":"Алгоритм","description":"Разработка алгоритма",
   "directions":["математика","информатика"],"amount":10000.50},
  {"title":"Исследование","description":"Проверка гипотезы",
   "directions":["математика"],"amount":5000}
]}
```

Пакет заявок проверяется целиком до записи: ошибка одного элемента отменяет весь пакет.
Повторный `rateApplication` заменяет прежнюю оценку того же эксперта. Среднее считается
по текущим оценкам, каждый эксперт имеет один голос на заявку. В ответах заявок есть
`id`, `ownerId`, `title`, `description`, `directions`, `amount`, а при наличии — `average`, `myScore`.
Gson не выводит отсутствующие значения. В ответах нет паролей или их хешей.

## Валидация и принятые решения по неоднозначностям

- Имена: 1–100 символов; название фирмы и заявки: 1–200; описание: 1–10000.
  Крайние пробелы текстовых полей удаляются.
- Логин: 3–64 символа, латинские буквы, цифры, `_`, `.`, `-`.
  Логины уникальны для обеих ролей без учёта регистра.
- Пароль: 8–128 символов, не только пробелы. Хранится PBKDF2-HMAC-SHA256,
  60000 итераций с индивидуальной случайной солью; открытый пароль не сохраняется.
- Фирмы уникальны по названию без учёта регистра. Эксперты — по паре имя/фамилия
  без учёта регистра: в ТЗ нет дополнительного идентификатора. Это учебное допущение:
  для реальных тёзок потребовался бы отдельный уникальный идентификатор.
- Направления: непустой массив, до 30 элементов, каждое 1–100 символов.
  Регистр и крайние пробелы не учитываются, дубликаты объединяются.
- Сумма заявки: строго больше нуля, не более двух знаков после точки. Деньги — BigDecimal.
  Пакет содержит 1–100 заявок; общее число пакетов и заявок участника не ограничено.
- Оценка — целое число 1–5. Числа передаются JSON-числами, строки — JSON-строками.
- Эксперт может искать и оценивать заявки, имеющие хотя бы одно его направление.
  При поиске по набору направлений действует «ИЛИ»; все запрошенные направления
  должны принадлежать эксперту. Собственные оценки доступны отдельным списком.
- Все данные регистрации и заявки неизменяемы. Отмена разрешена только владельцу.
  Удаление участника удаляет его заявки и оценки этих заявок; удаление эксперта — его оценки.
  Удаление аккаунта аннулирует все его токены. После удаления можно зарегистрироваться снова.
- Каждый вход создаёт новый UUID-токен. Несколько одновременных сессий допустимы;
  logout аннулирует только предъявленный токен.
- В момент `now >= X` запрещены регистрация, заявки, оценки, их удаление и удаление
  аккаунтов. Последнее ограничение сохраняет исходные данные итогов. Вход, выход,
  чтение заявок и результатов остаются доступны. До X результаты недоступны.
- Заявки без оценок не финансируются. Ранжирование: среднее по убыванию,
  сумма по возрастанию, при полном равенстве — случайно. Для сравнения средних
  используются точные произведения сумм и числа оценок, без ошибок округления.
- Среднее должно быть строго выше порога. Слишком дорогая заявка пропускается,
  после чего рассматривается следующая. При достижении порога распределение прекращается.
  Остаток не распределяется. Пустой конкурс возвращает весь фонд в остатке.
- Случайный порядок полных равенств выбирается однократно при первом запросе итогов
  после X. Итоги кешируются, поэтому повторные запросы возвращают тот же результат.

Эти решения явно уточняют места, не определённые в ТЗ; их можно согласовать с преподавателем.

## Архитектура

`тест → Server → CompetitionService → CompetitionDao → CompetitionDaoImpl → Database`

- `server`: тонкий фасад, только делегирование сервису.
- `service`: JSON, DTO, валидация, авторизация, правила конкурса и обработка ошибок.
- `dto.request`, `dto.response`: независимые типы запросов и ответов.
- `model`: неизменяемые Java records, без доступа к другим слоям.
- `dao`, `daoimpl`: интерфейс доступа к данным и реализация делегирования хранилищу.
- `database`: singleton с коллекциями; у каждого экземпляра Server отдельное пространство
  конкурса. Коллекции не выдаются наружу; DAO получает снимки списков.
- `exception`: исключение с машинным кодом и сообщением; сервис преобразует его в JSON-ошибку.

Операции одного сервера синхронизированы на сервисе: пакетная запись и подведение итогов
атомарны относительно других запросов. Сервисы не обращаются к Database напрямую.
Тесты используют только Server, ServerResponse и JSON, без доступа к внутренним слоям.

## Тестирование

37 автоматических проверок: успешные и ошибочные регистрации, уникальность, сессии,
права ролей, атомарность пакета, свои/чужие заявки, направления, изменение/удаление
оценки, каскадное удаление, точность денежных сумм, ранжирование, пропуск дорогих заявок,
порог, отсутствие оценок, случайные равенства со стабильными итогами, граница X,
изоляция нескольких серверов. Нет отключённых тестов.

GitHub Actions выполняет `mvn -B clean verify` при push и pull request на Java 17.

## Коммиты и публикация

Подключить проверку перед каждым локальным коммитом:

```shell
git config core.hooksPath .githooks
```

Hook запускает `mvn test` и запрещает коммит при ошибках.
При нестандартном расположении Maven можно указать путь через переменную `MAVEN_EXECUTABLE`.
На Windows commit выполняется из Git Bash или среды с Maven в PATH.

Проект не содержит секретов и подходит для публичного учебного репозитория.
После создания пустого репозитория на GitHub:

```shell
git remote add origin https://github.com/YOUR_ACCOUNT/grant-competition.git
git push -u origin main
```

Проверяющий должен иметь доступ к репозиторию. Ссылку на него нужно отправить через
соответствующий раздел учебного портала самостоятельно.
